## 最终架构与兼容性

设计器使用正式 `fields` 驱动 Schema、保存判断和历史；`resizeFields` 仅驱动画布预览。缩放起点保留原始字段，预览从起点计算以保持推挤结果一致；pointerup 提交，pointercancel / Escape 丢弃。布局预览跳过动画测量，正式变化后测量受影响行、后续行与跨越容器，保留未变化区域的测量缓存。稳定事件封装在 layout effect 中更新内部引用，属性面板使用 memo 避免预览穿透。

运行时每个已挂载表单拥有一个 store。普通控件订阅自身值、公式错误和校验错误；分组负责结构布局；HTML/TSX 自定义组件仍订阅完整 values。store 先更新所有变化快照，再通知订阅者，批处理中不暴露部分字段更新。`onValuesChange` 仍收到完整数据；同步字段脚本执行后才发布；提交读取 store 最新值，维持提交后校验时机和异步校验过期结果保护。

关联选择和回填通过事务 Context 合并，多次字段脚本写入的变化源被收集，事务末尾统一公式求值和校验。默认值、外部补丁、didMount 脚本也通过同一 store 发布路径；初始化/提交仍允许完整公式检查。公式编译计划按不可变 Schema fields 数组引用缓存，Schema 引用变化重建；循环、非法引用和已有公式函数机制保留，无关公式错误在增量求值中保留。

子表保留既有 20 行默认分页、增删与其他原有操作。行索引变化后校验键和更新回调随之更新；编辑单个值不执行无关编辑器，但子表父层仍需遍历当前页以生成 React 元素。真实富文本和 iframe 未替换，稳定空配置与回调减少无效更新；iframe 仍使用完整 values 消息协议与现有隔离、补丁策略。一次同步事务只发布一次完整 values，因此不会为关联回填的中间快照发送消息。

## 更新范围与性能数据

### 组件执行次数

使用 Vitest / Testing Library，真实 renderer 搭配可计数的成员编辑器替身，输入后记录编辑器函数执行次数。这是更新范围证据，**不是实际成员控件耗时或浏览器 FPS**。

| 场景 | 优化前无关编辑器执行次数 | 优化后无关编辑器执行次数 |
| --- | ---: | ---: |
| 50 字段，编辑一个 | 98 | 0 |
| 150 字段，编辑一个 | 149 | 0 |
| 300 字段，编辑一个 | 299 | 0 |
| 嵌套分组 300 字段 | 未单独采集旧实现 | 0 |
| 20 行 × 20 列子表 | 未单独采集旧实现 | 0 |

50 字段旧实现观测包含额外一次生命周期更新，因此为 98，不能改写成 49。旧实现执行新增的隔离断言时三个规模均失败；新实现通过。设计器 300 字段从未选中到选中执行 1 个叶字段，切换选择执行 2 个叶字段，索引遍历计数为 0；尾行缩放预览测量为 0，结束测量为 1。这个夹具不代表所有复杂容器只需一次测量。

### 公式 CPU 微基准

环境：Windows x64，Intel Core Ultra 7 265H，Node v24.13.0；每夹具预热 20 次、采样 200 次，同进程比较改动前保存的源码和改动后源码。单位毫秒，仅计公式函数 CPU 时间，不含 React、布局、绘制、网络或设备输入。

| 夹具 | 优化前 P50 / P95 | 优化后 P50 / P95 |
| --- | ---: | ---: |
| 50 普通字段 | 0.0031 / 0.0084 | 0.0006 / 0.0009 |
| 150 普通字段 | 0.0072 / 0.0117 | 0.0009 / 0.0045 |
| 300 普通字段 | 0.0106 / 0.0168 | 0.0006 / 0.0009 |
| 100 公式逆序链 | 28.1805 / 37.4029 | 0.0163 / 0.0708 |
| 100 公式分支 | 0.4452 / 1.0802 | 0.0160 / 0.0271 |

普通字段数据处于微秒量级，对运行时噪声敏感；不应把对应比例宣传为整页收益。逆序链减少多轮解释与收敛遍历，是本次最明确的公式 CPU 改善。原始数据见 [formula-benchmark.json](form-performance-evidence/formula-benchmark.json)。

理论变化：公式计划首次构建仍需遍历 Schema 与依赖；后续定位受影响链路使用反向依赖，受影响公式按拓扑顺序求值一次。store 发布仍需比较已缓存字段快照，完整 `onValuesChange` 和 iframe 消息仍承载完整值对象；这些部分没有变成常数成本。密集布局的多轮碰撞重排最坏复杂度仍可能较高。

## 复现与后续验收

1. 保留当前工作区，安装既有锁文件依赖；先处理 `/agent` 构建阻塞，再使用同一 Next 生产构建配置运行优化前和优化后版本。优化前基准应使用本次改动前快照，不能直接用 HEAD 覆盖包含其他改动的工作区。
2. 使用相同浏览器版本、视口、设备、节流设置、登录态和脱敏夹具；每轮先预热，再至少采集 200 次输入/选择/缩放，分别记录性能面板事件耗时、长任务与布局耗时，计算 P50/P95。
3. 夹具覆盖 50/150/300 普通字段、嵌套 300 字段、20×20 与多页子表、100 公式链/分支/逆序/循环、混合重控件。输入与初始挂载分开记录，固定控件类型；目标是 300 字段输入 P95 至少下降 30%。
4. 用 React Profiler 或开发计数器确认无关控件执行范围；计数器测量和生产性能测量分开，避免 instrumentation 本身污染结果。浏览器轨迹如未达标，先按主线程占用定位再继续优化。

## 剩余瓶颈与适用规模

本次自动化覆盖到 300 普通/分组字段与一页 400 个子表编辑器，实际浏览器覆盖 73 控件、联系人 21 行。这是已验证范围，不是容量或流畅度上限承诺。真实 HeroUI、富文本、成员弹层及自定义脚本的成本因配置与设备而变，不能用替身渲染测试外推。

保留真实 DOM 意味着初始挂载、样式计算、滚动绘制与可访问性树仍随控件数增长。密集推挤布局可能波及整个容器；提交后完整校验、完整 values 通知和 iframe 序列化仍有规模成本。快照比较、历史序列化和 deep clone 主要转移到正式提交边界，超大表单仍应单独分析。

建议优先解除生产构建阻塞并补齐配对轨迹，然后处理 `PressResponder` 警告、混合控件初始挂载与自定义脚本热点。按用户约束，本次未采用虚拟滚动或简化控件预览。Schema 缓存依赖不可变引用；外部消费者应按既有 React 约定替换字段数组/对象，原地修改嵌套对象的脚本另需专项验证。
