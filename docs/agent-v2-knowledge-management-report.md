# 三类知识库管理首批实现记录

日期：2026-11-06。范围：知识管理 K1 的首个可运行代码批次，不包含解析 Worker、Embedding、向量索引、混合检索、重排和 Agent 引用；不宣布知识库 RAG 或完整 K1 验收完成。

## 页面入口

- 应用知识库：独立页面 `/{appId}/settings/knowledge`，在应用设置导航中与“基础设置”并列；例如 `/APP_BB05CB9381E14C2BAD63/settings/knowledge`，不硬编码应用 ID。
- 全局知识库：`/settings/knowledge`，位于设置的 AI 员工分组。
- 员工自带知识：运营中心 `/ai-employees` 的员工编辑模态框增加知识区。先保存员工，再上传文档；客户平台在 AI 员工详情弹窗的「知识库」标签只读查看与下载；原独立页面及设置菜单入口已移除。

前端使用共享 `web/features/knowledge/KnowledgeManager.tsx`，HeroUI 组件、Gravity 图标，不导入旧 Agent，不新增 CSS Module。没有选择文件即自动提交的隐式动作：上传按钮选择知识文档后开始知识上传，这是明确的知识管理操作，与会话发送框仅发送后上传的草稿合同不同。

## 实际实现

客户知识支持新建库、列表、原始二进制上传、同文档更新不可变版本、版本列表、下载、删除文档及删除库。创建与上传有服务端幂等合同；上传锁定知识库并检查累计大小，文件与版本指针在同一事务提交。下载重新检查当前权限，作为 attachment 返回并禁用缓存和 MIME 嗅探；不直接执行或内联文档 HTML。

K1首次交付时文档状态仅为 `stored`。2026-11-09 K2 已编码自动解析任务、状态及分块预览，见[解析报告](agent-v2-knowledge-parsing-report.md)；完整知识检索仍未开放，不将解析完成当作 RAG 可用。

初始限额：单文档 8 MiB；客户知识库含历史版本合计 2000 份 / 1 GiB；每个员工包当前有效文档最多 20 份 / 40 MiB。支持 UTF-8 TXT/Markdown/CSV/TSV、PDF、DOCX、XLSX、ODS、PPTX 原件；校验文件签名、Office 必需结构及声明解压大小，不宣称这等同完整解析成功。宏和脚本不执行。

知识权限新增全局 `knowledge.global.view/manage` 及应用 `app:{id}:knowledge_view/knowledge_manage`，同步后端目录、前端目录和角色应用权限选项；manage 包含查看。应用知识还要求 `app:{id}:display`，不自动授予普通角色权限。第一批授权粒度为全局类型及应用类型，尚无每个独立知识库的单独角色授权 UI；有类型管理权的用户可以管理该范围的库，不能将其描述为细粒度库 ACL 已完成。

数据库 `knowledge_deployment_scope` 持久保存当前数据库对应平台的范围 UUID。兼容列名 `tenant_id` 引用该部署范围，不使用用户主部门 ID，也不会因许可证续签变化；每个客户独立数据库，未引入多租户管理。

## 运营中心与安装同步

运营中心新增 `employee_knowledge_documents` SQLite 表及员工删除清理触发器，初始化时自动创建，原有员工/Skill 字段不改变。知识增删与员工版本递增使用同一 SQLite 事务；知识移除保留必要幂等元数据并清空原件字节，不创建内容备份。产品编辑保存不覆盖知识资源。

安装包响应新增可选 `knowledge` 字段：`formatVersion:1`、`version`、`documents[{id,name,size,sha256}]`。资源通过有许可证校验的独立二进制下载端点传输；不把文档正文放入许可证 JWT。旧包缺字段视为无知识。

客户安装/更新沿用现有许可证、版本发现和安装接口，先下载并校验全部知识资源，再在已有安装数据库事务内同步原件。版本必须与员工包一致、文件 ID 唯一、hash 和大小正确；下载失败不发布新知识和员工包。下载期间发生撤回会导致本次安装失败并保留原安装。

知识只读访问同时检查当前员工使用权、有效许可证、实际安装及本地安装 manifest 版本；员工管理员但没有员工使用权的普通用户不能因此读取员工知识。新安装版本只展示匹配的文档集合；旧数据库快照保留待后续明确保留期和回收任务，不自动删除用户资源。不运行 pip/npm、不构建向量、不阻塞员工安装等待索引。

本批没有运营端撤回后实时推送到客户的失效传播，也不实现活跃 Agent 的知识版本快照：知识工具尚未开放。客户更新前仍可能访问旧安装的资料；远端即时撤回、活跃任务版本引用和历史数据回收保留为后续验收门槛，不宣称已达到专项设计的全部同步要求。

## 迁移与启动

平台新增 `m20261106_000114_knowledge_management`，由现有启动迁移机制追加知识部署范围、库、文档、版本和上传幂等记录。未安装 pgvector，没有修改历史迁移。新增迁移已在真实 PostgreSQL 的随机隔离 schema 执行并通过 HTTP 测试；尚未在当前业务 schema 应用，也未完成完整平台空库验收。

1. 运营中心按其现有 `./start-dev.ps1` 启动或重启 API/Web，自动初始化新增 SQLite 表。
2. 客户平台按 `./scripts/start-dev.ps1` 启动或重启，应用平台迁移并加载新版 API 与 Web。
3. 为需要使用的普通角色分配新增知识权限；本批不改正式角色、许可证或员工包内容。
4. 在运营中心编辑测试员工上传文档，客户 AI 员工市场发现新版本后执行更新安装，再查看员工自带知识。

API OpenAPI 与生成 SDK 已同步。Next `/api/knowledge/[...segments]` 对上传与下载使用二进制文件代理，其他接口使用现有 JSON 代理；知识前端通过生成 SDK 调用，不手写 fetch 合同。

## 精简手测

1. 独立测试应用设置的“应用知识库”页面创建“知识验收-应用”，全局创建“知识验收-全局”，分别上传中文 TXT、Excel、PDF；下载对比原件。
2. 同一文档更新版本，版本列表能下载新旧原件；删除文档及库有确认，刷新后不再显示。
3. 普通角色只有应用显示但没有知识查看时不可读，只有知识查看不可上传；全局管理不可越过应用权限。
4. 运营中心测试员工上传文档，确认员工版本变化；客户市场更新后出现只读文档。移除文档后再次更新，当前列表移除对应资料。
5. 无效许可证、未安装或无员工使用权时不能读取；跨应用/跨用户未授权下载被拒绝。
6. 模拟知识下载失败、内容校验失败或安装响应丢失，确认旧员工及资料保留，再重试核对。

使用明确命名的测试资源，不修改客户正式业务数据。回退禁用新知识入口并停止更新，保留新增表和原件，不自动执行降级删除、不恢复 DSH。
