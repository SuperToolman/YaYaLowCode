# 应用市场开发计划

## 1. 目标与边界

本文基于当前两个项目的实现制定后续计划：

- 低代码平台：`E:\OverPorject\yaya-low-code`
- 运营管理平台：`E:\OverPorject\yaya-operation-center`

目标是完成下列闭环：

1. 应用创建者可从低代码平台提交应用上线申请。
2. 运营人员可查看申请中的应用、表单、自定义页面、工作流和集成自动化，并审核。
3. 审核通过的版本自动出现在运营端 `/application-products`。
4. 低代码平台的应用市场可浏览运营端已上架应用。
5. 已授权的目标平台可下载并安装应用包。
6. 安装后应用可创建数据、运行自动化和工作流，且不携带源环境运行数据、人员和密钥。

### 不在首期范围

- 迁移业务记录、附件、流程实例、审批任务、评论与运行日志。
- 迁移用户、组织、角色及用户与角色的直接绑定。
- 迁移第三方密钥、Token、数据库口令和任何其他凭证明文。
- 跨低代码平台版本的无限兼容；首期采取明确的包格式与平台版本兼容校验。

## 2. 当前实现基线

### 已有能力

- 低代码端会生成结构 ZIP，并向运营端 `POST /api/application-submissions` 提交。
- ZIP 当前固定包含应用基础资料、导航、表单定义、全部已保存 Schema、存储定义和全部自动化流程定义。
- 工作流流程定义属于 `automation_flows` 中 `flow_type=process` 的记录，随 `automations/index.json` 一并导出。
- 运营端保存申请快照，管理员可同意或驳回；已通过记录可在 `/application-products` 显示。
- 低代码端可读取运营端的已通过记录，并将本环境中同 `appId` 的既有应用标记为 `online`。

### 必须替换的现状

当前“同步”不是安装：它只给本地已有同 ID 应用写入 `deployment_type=online`。因此无法将运营端一个应用安装到另一套低代码环境，也无法处理 ID 冲突、资源依赖、更新、回滚或卸载。

后续必须采用两类身份：

| 概念 | 含义 | 归属 |
| --- | --- | --- |
| `publisher_app_id` | 发布者源应用的稳定标识 | 应用包与运营端目录 |
| `release_id` / `version` | 某一次不可变发布版本 | 运营端 |
| `installation_id` | 目标环境的一次安装记录 | 目标低代码平台 |
| `local_app_id` | 目标环境中新创建的应用 ID | 目标低代码平台 |

安装导入时必须创建新的本地应用、表单 UUID、自动化 UUID 与导航 ID；不能复用发布环境的数据库主键。

## 3. 目标架构

```text
发布低代码平台                         运营管理平台                     安装低代码平台
应用配置/表单/自动化
      |                                      |                                  |
      +-- 构建并校验 release package ------> release / listing / 审批            |
                                             |                                  |
                                             +-- 市场目录、包下载授权 ---------->|
                                                                                |
                                                                        校验/解包/ID 映射
                                                                                |
                                                                        创建本地应用资源
                                                                                |
                                                                        安装配置、启用、运行
```

职责划分：

- **低代码 API**：导出、预检、安装、升级、卸载、运行时资源重建；持有本环境的安装记录。
- **运营 API**：发布版本存储、审核、市场上架状态、包下载授权、审计。
- **低代码 Web**：发布向导、申请状态、市场浏览、应用详情、安装与升级交互。
- **运营 Web**：审核详情、包资源清单、风险与兼容性信息、上架管理。

## 4. 包格式 V2

当前 V1 的 ZIP 和 Base64 快照可保留为兼容读取，但新发布一律改为 V2。运营端保存原始 ZIP 文件或对象存储引用；不要将大包长期作为 SQLite JSON 字段返回给列表接口。

### 4.1 Manifest

`manifest.json` 至少包含：

```json
{
  "formatVersion": 2,
  "packageType": "yaya-application",
  "publisherAppId": "app_xxx",
  "version": "1.2.0",
  "platformCompatibility": { "min": "x.y.z", "max": "x.y.z" },
  "createdAt": 0,
  "checksums": {},
  "dependencies": { "plugins": [], "skills": [], "connectors": [] }
}
```

### 4.2 必须导出的资源

| 资源 | 包内文件 | 导入策略 |
| --- | --- | --- |
| 应用基础信息 | `application.json` | 新建本地应用，保留发布标识为外部引用 |
| 应用业务上下文与应用设置 | `application-settings.json` | 导入不含人员/密钥的设置 |
| 导航 | `navigation.json` | 按新表单映射重建目标引用与排序 |
| 表单定义 | `forms/index.json` | 为每个源 UUID 生成目标 UUID |
| 当前表单 Schema | `schemas/index.json` | 重写表单关联、字段关联和其他资源引用 |
| 表单视图 | `views/index.json` | 用新表单 UUID 和新视图 UUID 重建 |
| 存储定义 | `storage-definitions/index.json` | 重新编译、创建目标存储；不带物理表名 |
| 自定义页面 | `defined-pages/index.json` 或 Schema 明确分组 | 导入其配置和受支持的 HTML/TSX 源；执行静态安全校验 |
| 自动化 | `automations/index.json` | 新建流程和版本，重写表单/流程引用 |
| 工作流 | `workflows/index.json` 或自动化内 `flowType=process` | 导入流程定义，不导入实例和任务 |
| 权限模板 | `permission-templates.json` | 导入角色权限模板，不导入用户绑定 |
| 连接器声明 | `connectors/index.json` | 只带类型、字段模式和配置占位；安装后由管理员绑定本地凭证 |

### 4.3 明确禁止写入包

记录、附件、工作流实例、任务、评论、自动化运行记录、用户、组织、用户角色绑定、密码、access token、API key、数据库连接密码、物理表名，以及服务器本地路径。

### 4.4 包构建与校验规则

- 按稳定顺序序列化，生成每个文件 SHA-256 与整包 SHA-256。
- 发布前校验 Schema、表单关联、自动化图、工作流图、导航引用和依赖清单。
- 发现缺失依赖、未绑定的敏感连接器或不支持的自定义页面能力时，阻断提交并返回可定位错误。
- 包版本遵循 SemVer：兼容变更递增 patch/minor，破坏性变更递增 major。

## 5. 数据模型与迁移

### 5.1 运营平台

将当前 `application_releases` 逐步迁移为以下模型。保留旧表读兼容，完成数据迁移后再移除。

| 表 | 核心字段 | 用途 |
| --- | --- | --- |
| `application_products` | `product_id`, `publisher_subject`, `publisher_app_id`, `name`, `description`, `status` | 市场商品，聚合多个发布版本 |
| `application_releases` | `release_id`, `product_id`, `version`, `package_uri`, `package_sha256`, `manifest_json`, `review_status` | 不可变发布版本 |
| `application_reviews` | `review_id`, `release_id`, `reviewer_id`, `decision`, `reason`, `reviewed_at` | 审批历史，不能覆盖 |
| `application_listing_versions` | `product_id`, `release_id`, `listing_status`, `published_at`, `withdrawn_at` | 哪个版本对市场可见 |
| `application_entitlements` | `subject`, `product_id`, `license_id`, `status`, `expires_at` | 哪个客户主体可安装哪个产品 |
| `application_download_audits` | `release_id`, `subject`, `requested_at`, `result` | 下载审计 |

运营端不应再将完整 `snapshot/packageBase64` 放进市场列表响应。市场列表只返回展示元数据与版本摘要；包通过单独、受授权的下载接口获取。

### 5.2 低代码平台

新增安装记录和资源映射：

| 表 | 核心字段 | 用途 |
| --- | --- | --- |
| `market_installations` | `installation_id`, `product_id`, `release_id`, `local_app_id`, `status`, `installed_at`, `updated_at` | 本环境安装状态 |
| `market_installation_resources` | `installation_id`, `resource_type`, `source_id`, `local_id` | 支持引用重写、升级、回滚和卸载 |
| `market_installation_events` | `installation_id`, `event_type`, `detail_json`, `created_at` | 安装、失败、升级与回滚审计 |
| `market_connector_bindings` | `installation_id`, `source_connector_id`, `local_credential_id`, `status` | 安装后连接器凭证绑定 |

应用实体增加只读的市场来源字段：`market_product_id`、`market_installation_id`、`market_release_id`。现有 `deployment_type/online_version/online_release_id` 不再承担安装状态。

## 6. API 设计

### 6.1 低代码 API

| 接口 | 作用 | 权限 |
| --- | --- | --- |
| `POST /api/apps/{appId}/releases` | 构建 V2 包、校验并提交运营端 | 应用创建者/管理员 |
| `GET /api/apps/{appId}/releases` | 查看本应用发布历史与运营审核状态 | 应用创建者/管理员 |
| `GET /api/market/applications` | 获取已上架市场目录摘要 | 已登录且许可证有效 |
| `GET /api/market/applications/{productId}` | 获取商品详情、资源摘要、兼容性与可安装版本 | 已登录且许可证有效 |
| `POST /api/market/applications/{productId}/installations` | 下载、校验、预检、安装 | `apps.import`/管理员 |
| `POST /api/market/installations/{id}/upgrade` | 安装指定新版本 | `apps.import`/管理员 |
| `POST /api/market/installations/{id}/rollback` | 回滚到指定已安装版本 | `apps.import`/管理员 |
| `DELETE /api/market/installations/{id}` | 卸载应用及由该安装创建的资源 | 管理员 |
| `GET /api/market/installations/{id}/preflight` | 返回依赖、冲突、凭证绑定和破坏性变更提示 | `apps.import`/管理员 |

安装接口必须是事务性工作流：先创建 `installing` 记录，下载与校验包，创建资源并写映射，编译存储，校验运行入口，最后切换为 `installed`。失败时回滚创建的资源，保留失败事件供排查。

### 6.2 运营 API

| 接口 | 作用 | 权限 |
| --- | --- | --- |
| `POST /api/application-submissions` | 接收包与提交元数据，验证许可证和摘要 | 有效低代码平台许可证 |
| `GET /api/application-submissions` | 审核队列及过滤 | 运营管理员 |
| `GET /api/application-submissions/{releaseId}` | 获取资源清单、包校验结果、只读详情 | 运营管理员 |
| `POST /api/application-submissions/{releaseId}/review` | 同意/驳回，必须记录理由 | 运营管理员 |
| `POST /api/application-products/{productId}/listing` | 上架、下架、切换市场版本 | 运营管理员 |
| `GET /api/market/applications` | 返回仅限展示的已上架目录 | 有效许可证 |
| `GET /api/market/applications/{productId}` | 返回商品详情与版本摘要 | 有效许可证 |
| `POST /api/market/applications/{productId}/download-ticket` | 根据授权签发短期下载票据 | 有效许可证且有 entitlement |
| `GET /api/market/downloads/{ticket}` | 传输 ZIP；一次性/短期有效 | 下载票据 |

## 7. 分阶段实施

### 阶段 0：确定发布合同

1. 固化 V2 manifest JSON Schema，并在两个项目共享相同的 schema fixture。
2. 定义“可迁移资源清单”和“禁止迁移资源清单”。
3. 确定首期支持的自定义页面能力；不支持的页面类型必须在发布前阻断，不能静默丢失。
4. 制定兼容策略：低代码平台版本、插件、Skill、连接器类型的最小/最大版本。

完成标准：两个服务均能对同一 V2 示例包执行 schema 与 checksum 校验。

### 阶段 1：完整导出与发布申请

1. 在低代码 `app_market.rs` 抽出 `ApplicationPackageBuilder`。
2. 补齐 V2 资源读取：应用设置、表单视图、权限模板、定义页面配置、连接器声明。
3. 将工作流流程作为明确资源导出，或保证 `flowType=process` 自动化流有单独断言测试。
4. 用二进制 ZIP 上传或对象存储上传；提交请求传包摘要、manifest 和元数据，不传 Base64 大字段。
5. 增加发布历史、构建失败原因和重新提交功能。

完成标准：一个含动态表、定义页面、工作流、自动化、视图和连接器声明的样例应用可生成可重复校验的 ZIP。

### 阶段 2：运营审核详情与应用管理

1. 运营端持久化产品、发布版本、审核历史、包元数据和包文件引用。
2. 将当前 `/applications` 改为审核队列，支持待审/通过/驳回/撤回筛选。
3. 新增申请详情页：基础信息、版本、manifest、表单清单、视图清单、定义页面、工作流图、自动化图、依赖与风险清单。
4. 审批操作必须填写驳回原因；同意可附审核备注。记录审核人、审核时间和不可变历史。
5. `/application-products` 改为真正的商品管理：当前上架版本、历史版本、上架/下架、版本切换。

完成标准：运营人员无需下载或解析原始包，即可在页面审查应用包含的表单和自动化；同意后版本出现在 `/application-products`。

### 阶段 3：市场目录与授权下载

1. 运营端提供受许可证认证的目录、详情、下载票据接口。
2. 市场列表只返回卡片所需的元数据，不返回 ZIP、完整 Schema、流程节点或凭证占位细节。
3. 增加 entitlement 校验；无授权用户可浏览策略按业务决定，但不得下载/安装。
4. 低代码 Web 新建“应用市场”页面，包含分类、搜索、详情、版本、兼容性、已安装状态和安装按钮。
5. 低代码 Web 不再在“我的应用”页面执行上线同步；该页面只显示本地应用和来源/安装状态。

完成标准：有权限的平台可在市场看到运营端 `/application-products` 中上架的版本，并可获得下载票据；无授权主体无法下载。

### 阶段 4：预检与安装导入

1. 实现 ZIP 下载、hash 校验、manifest 校验、大小/文件数/路径遍历保护。
2. 预检平台版本、资源类型、插件/Skill/连接器依赖、名称冲突和现有安装状态。
3. 生成源资源 ID 到本地资源 ID 的映射，并在一个数据库事务中创建应用、表单、Schema、视图、导航、自动化和流程。
4. 在所有资源创建后重写内部引用：导航目标、关联字段、视图引用、自动化节点、工作流审批人规则中的资源引用。
5. 重建存储定义与物理表；不从包写入源环境物理表名。
6. 导入后保持连接器为 `needs_binding`，要求目标环境管理员配置本地凭证；未绑定连接器的自动化不得启用。
7. 运行安装后健康检查：默认导航存在、所有表单可读取、流程图合法、自动化图合法、存储已编译。

完成标准：在干净目标环境安装样例应用后，表单可录入，工作流可发起，纯本地自动化可执行；需要凭证的自动化显示待绑定且不会误执行。

### 阶段 5：升级、回滚、下架与卸载

1. 对比安装版本与目标版本，按资源映射生成升级计划：新增、修改、删除、人工处理项。
2. 对存在数据的表单执行迁移前检查；破坏性字段删除或类型变更必须阻断或要求明确确认。
3. 每次升级前保存安装快照与版本指针，支持事务失败回滚。
4. 运营端下架仅阻止新安装；已安装实例的可用性、更新策略和安全下线规则需明确配置。
5. 卸载前检查数据与被其他本地资源引用的依赖；默认采取软删除/归档，再允许管理员永久清理。

完成标准：同一商品可从 V1 升级至 V2 并回滚；下架不损坏既有已安装应用。

## 8. 前端页面与交互

### 低代码平台

- 我的应用：显示“本地创建”或“市场安装”、安装版本、可升级状态；发布入口改为发布向导。
- 发布向导：资源概览、依赖检查、敏感配置排除提示、版本和发布说明、提交结果。
- 应用市场：列表、搜索、分类、详情抽屉/页面、版本、兼容性、资源摘要、安装预检与安装进度。
- 已安装管理：凭证绑定、升级、回滚、卸载、安装日志。

### 运营管理平台

- 应用申请管理：审核队列与详情，不只显示表格摘要。
- 应用管理：产品维度聚合、每个版本的审批记录、当前上架版本、上架/下架控制。
- 审计日志：记录提交、审核、上架、下架、下载票据、下载结果与失败原因。

## 9. 安全与可靠性要求

- 所有跨平台调用继续使用平台许可证认证；审核接口只允许运营管理员。
- ZIP 必须防 Zip Slip、Zip Bomb、重复文件、超大文件和 checksum 不匹配。
- 不返回完整包给无 entitlement 的主体；市场列表与详情默认最小化暴露。
- 包与下载票据要记录 SHA-256、请求主体、时间和结果。
- 安装器不能执行包内任意代码；自定义页面仅允许平台支持的受限运行模型，并进行静态校验。
- 凭证永不出包。目标环境仅保存对本地凭证 ID 的绑定关系。
- 操作应幂等：重复提交、重复下载、重复安装请求不能生成重复应用。

## 10. 测试与验收

### 自动化测试

1. 包构建：验证 V2 包恰好包含必需资源，且绝不含记录、用户、密钥、物理表名。
2. 包校验：损坏 ZIP、hash 不符、非法路径、未知格式、缺失依赖均被拒绝。
3. 审核：待审、同意、驳回、重复审核、审核历史和权限控制。
4. 市场隔离：无许可证、无 entitlement、不同主体不可下载包。
5. 安装：空环境安装、资源 ID 重映射、关联字段/导航/自动化引用重写、失败回滚。
6. 运行：安装后的动态表录入、工作流提交审批、自动化触发；缺失凭证时受控停用。
7. 升级：兼容升级、破坏性升级阻断、回滚、下架后已安装应用可用性。

### 端到端验收场景

1. 在发布环境创建含动态表、定义页面、工作流、两条自动化和一个需凭证集成的应用。
2. 提交 V2 申请，运营端详情完整显示资源清单与风险。
3. 审核通过并上架，运营端 `/application-products` 显示该产品与版本。
4. 另一许可证主体的低代码平台从市场安装；验证未授权下载会被拒绝。
5. 在目标环境绑定本地凭证后，验证表单、工作流及自动化正常运行。
6. 发布 V2 新版本，目标环境预检、升级和回滚均可验证。

## 11. 实施顺序与里程碑

| 里程碑 | 交付物 | 对应目标 |
| --- | --- | --- |
| M1 | V2 包合同、完整导出、发布历史 | 1 |
| M2 | 运营审核详情、审核历史、产品管理 | 2、3 |
| M3 | 市场目录、授权与下载票据 | 4 |
| M4 | 安装器、预检、资源映射、凭证绑定 | 5、6 |
| M5 | 升级、回滚、下架、卸载 | 6 的持续运营 |

开始编码前，应先以一个“动态表 + 定义页面 + 工作流 + 自动化 + 连接器”的样例应用作为固定验收 fixture。它会同时约束包格式、审核详情和安装器，避免各阶段分别实现后再发现资源引用无法闭环。
