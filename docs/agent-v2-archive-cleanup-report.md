# AgentV2 归档批量删除调度调整

日期：2026-11-09。状态：代码调整；仅执行编译和定向静态检查，没有删除用户会话、重启现有服务或执行回归/浏览器测试。

## 原问题

原清理器使用全局数据库互斥锁，每次只处理一个会话，结束后固定等待5秒；事务中等待执行器文件删除。24条请求仅调度间隔即接近两分钟。执行器原先在异步运行线程内同步删除整个会话环境，并持有全局锁，Python venv/node_modules 的大量小文件放大了影响。接口还将未归档、已删除受理、活跃执行合并为同一错误。

## 调整

- 每个 API 实例固定3个清理消费者，积压连续处理，无每条5秒间隔；空闲时通知唤醒或每2秒检查。
- PostgreSQL `FOR UPDATE SKIP LOCKED` 原子领取后立即提交，文件清理不占用数据库事务/行锁；使用领取时 updated_at 作为执行令牌。领取中断超过5分钟可重新接管；最终清理与失败更新核对令牌，旧处理者不能覆盖新状态。
- 文件成功删除后再开启数据库清理事务；统一 session→deletion 锁顺序，保留原清理内容与原子性。外部文件和数据库仍不能跨介质原子提交，数据库失败时通过幂等重试完成，不虚报成功。
- 执行器保留会话独占锁和删除标记，发布标记后释放全局锁；实际递归删除转入 `spawn_blocking`。不同会话的文件清理可并行，不阻塞异步处理线程。
- 为避免并行扫描读到半删除的执行记录，在元数据锁内将已核对的任务目录同卷移动至该会话专属删除暂存目录，立即参与本轮物理删除；失败重试继续清理。没有复制、归档或保留备份，不撤销已发生的业务效果。
- 会话归属、目录范围、符号链接、活跃/结果不确定脚本等检查继续保留。执行器不可用时仍不能宣称文件已删除，普通会话也保留该检查，避免遗漏历史执行目录。
- 删除端点的内部等待上限由35秒改为180秒，其他执行器调用保持原上限。此上限并非保证文件能在该时间完成；超时后可能仍在清理，重试受会话锁保护。
- 重复删除 queued/running 返回既有状态，不报冲突、不更新领取时间；failed 由用户重试重新排队。未归档、已受理不能恢复、脚本结果待核对分别提示。归档和删除受理均复用会话取消命令；清理等待任务及脚本停止。
- 执行器错误按活跃执行、待核对、文件占用、目录归属、读取失败、认证失败、服务不可用等区分；前端清理失败区显示安全原因，不回显目录与密钥。
- 普通归档卡片仅显示未提交删除的会话；已受理项收起为等待/清理数量，失败项单独列出并允许批量重试。2秒刷新持久状态，清理后不再展示。摘要仅统计当前已加载分页，不冒充所有分页总量。

## 检查与使用

API 与 execution manager 使用独立 `agent-v2/target/validation` 做 cargo check；归档页面与卡片做定向 ESLint。未新增迁移、公共 DTO 或 HTTP 路由，沿用现有状态字段、OpenAPI/SDK/BFF。

Web TypeScript 检查仍报告已有 `app/components/my-fields/MyTable.test.tsx:66` 的 children 类型错误；归档改动未产生新的类型错误。没有运行回归、真实数据库并发测试、浏览器或24条实际删除验收，不把静态检查等同删除链路实测。

配套重启 API、execution manager 与 Web 后生效，可沿用 `./scripts/start-dev.ps1`。queued 自动继续，旧 running 超过5分钟后可接管；已经 failed 的会话在失败区重试。未结束 run 由归档/删除取消，清理消费者等待任务与脚本停止；outcome_unknown 执行仍须先核对，不能绕过检查强删。

回退前停止清理消费者及进行中的删除请求；保留数据库和会话文件，不自动恢复已删除内容。旧执行器不认识删除暂存目录，不应在尚有暂存残留时回退；需先由新版完成清理。当前改动未处理或删除截图中24条真实记录，其具体阻塞原因仍以升级后持久错误与服务日志为准。


## 归档、停止与删除状态一致性补充（2026-11-09）

发现此前归档接口只拒绝未结束 run，没有主动取消，也没有将脚本停止确认纳入同一生命周期。任务终态与脚本实际停止是两个状态，旧归档数据仍可能存在待停止脚本。目录 SQL 已只查询 archived_at 非空的条目；其他标签页恢复后，未刷新的页面会残留旧条目。

- 归档在原 session 锁与事务内调用公共 `Store::submit_in_transaction` 的 Cancel 命令，再保存归档状态。取消队列/等待/暂停任务，运行任务进入 cancel_requested，并使未执行确认失效。前端运行时的归档按钮改为“归档并停止当前任务”，不再要求先手动停止。归档成功表示停止已请求，不代表进程已确认退出。
- 删除受理对旧归档数据也补发 Cancel；正常停止中的任务不再导致删除接口失败。清理领取 SQL 排除非终态 run 与 queued/running execution，等待现有 Worker/执行器停止确认，不通过伪造终态强删文件。服务未启动时等待不会虚报完成。结果不确定仍明确拒绝或由执行器报告待核对。
- 已受理删除立即应用服务端结果到前端列表，不依赖后续刷新成功才隐藏可点击卡片。同步操作锁避免同一页面重复提交，刷新失败不再将已受理操作报为删除失败。跨页状态在页面聚焦/可见时刷新，普通状态每10秒刷新，存在清理请求时每2秒刷新；其他标签页修改与当前请求之间仍由服务端事务和幂等规则判定。
- 本次 API cargo check 与归档页、会话操作、目录 hook 定向 ESLint 通过。未运行数据库/浏览器/回归测试，未删除真实会话，未重启运行服务。无需迁移或变更公共 DTO。API、Worker、执行器需运行以完成停止与清理；重启 API、刷新 Web 后使用新逻辑。
