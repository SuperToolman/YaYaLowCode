# AgentV2 低代码开发工程师能力调整方案

日期：2026-11-06。

状态：架构决策、能力合同与分批实施计划，尚未实施本方案中的新增能力。本文不修改员工商品、安装包、许可证、用户 RBAC 或客户业务数据，不代表复杂应用开发已经验收通过。

关联：[AgentV2 主架构](agent-v2-architecture.md)、[开发计划](agent-v2-development-plan.md)、[验收矩阵](agent-v2-acceptance.md)、[现阶段计划](agent-v2-current-stage-plan.md)、[知识库与 RAG 设计](agent-v2-knowledge-rag-architecture.md)。本文中的新工具名称、响应字段和阶段划分属于建议合同，正式编码前必须核对既有服务及兼容性，不直接当作已存在的接口。

## 1. 结论与调整目标

保留独立 Rust、Rig 模型执行循环、平台授权工具、持久任务、写入确认、业务事务和工作区的现有架构。复杂低代码开发的主要缺口是权威产品规范的供给、跨资源设计约束、诊断修正及真实业务验收，不能仅通过增加提示词、开放更多工具或建设向量库解决。

目标员工能够完成：

**理解需求 → 识别待确认业务规则 → 读取平台能力和当前应用 → 按需查询组件/节点规范 → 形成设计 → 生成 Schema/流程定义 → 校验并修正 → 提供具体预览 → 用户确认 → 事务保存 → 读取验证 → 如实交付。**

必须支持没有知识资料、没有历史案例、没有现有表单的空应用。用户无需自行编写或上传平台组件规范。知识库提供补充参考，不是开发能力的启动条件。

“低代码开发工程师”不能仅以工具调用成功定义能力：设计需要能够在实际设计器打开、由运行时正确渲染，并符合已确认的业务行为。涉及外部系统时，还必须区分设计可保存、配置可连通和真实业务执行三种结果。

## 2. 当前基线与真实缺口

本次结论来自代码检查，不是对当前安装员工包、所有组件或自动化流程的端到端认证。

| 方向 | 当前代码基线 | 本方案要求补齐 |
| --- | --- | --- |
| 空应用起步 | 有创建应用、空白表单、导航等工具 | 从需求拆解到依赖排序、资源创建与验证的完整方法 |
| 表单基础合同 | 有根结构、布局、组件类型及少量通用属性说明 | 所有正式支持组件的完整、版本化合同 |
| 表单设计写入 | 有完整 Schema 保存、T31 补丁及持久确认 | 按组件诊断、业务语义检查和修正闭环 |
| 高级组件 | 合同列出子表、关联字段等名称 | 属性、父子结构、资源引用、限制及有效案例 |
| 自动化 | 有列表、流程图读取、创建、删除；创建调用公共业务服务 | 节点合同查询、变量/类型检查、独立更新路径及安全验证 |
| 工作流 | 有流程定义及运行信息读取工具 | 写能力按实际服务核对；不能将工作流表单 Schema 写入等同审批流程编排 |
| 业务知识 | 三类知识原件管理已有增量实现 | 解析、索引、检索及引用仍按 RAG 专项推进 |
| 员工实际配置 | 本次未逐项核对正式安装包的提示词和能力 | 经正常运营发布与安装流程确认，不能根据商品名称推定能力 |

关键代码入口：

- `api/src/modules/forms.rs`：`get_form_schema_contract` 当前基础说明。
- `agent-v2/core/src/tools.rs`：工具描述符、别名和员工能力映射。
- `api/src/modules/agent_v2/tools.rs`：平台工具授权与业务服务调用。
- `api/src/modules/agent_v2/design.rs`：现有设计补丁、基准与写入检查。
- `api/src/modules/automations/graph.rs`：自动化图校验，已有图检查不等同全部节点业务校验。
- `web/features/form-runtime/field-registry.ts`、设计器的 `designer-types.ts` / `designer-schema.ts`：组件运行与设计结构的候选核对来源。
- `web/features/automation-editor`：条件规则与字段映射等产品合同的候选核对来源。

以上是核对入口，不宣称任意一个文件已经包含全量权威规范。

## 3. 架构分工：平台工具、知识库、Skill 与 MCP

| 层次 | 内容 | 维护责任与权威性 |
| --- | --- | --- |
| 产品合同 | 组件属性、Schema、节点类型、变量语法、版本限制 | 平台开发维护；随部署版本交付，是生成和校验的权威依据 |
| 实时应用事实 | 当前表单、字段、资源版本、自动化、可访问记录 | 公共业务服务按当前用户权限提供，不从过期知识索引代替读取 |
| 业务知识 | 客户制度、领域术语、业务文档 | 应用/全局知识库提供；缺失时追问或提出待确认假设 |
| 开发经验 | 设计步骤、建模方法、行业案例 | 员工 Skill/自带知识；不得覆盖当前产品合同 |
| 操作执行 | 查询、校验、预览、确认、保存 | V2 工具调用公共业务服务，继续持久化与授权 |
| 外部接入 | 对外提供相同查询与操作 | 未来通过 MCP 适配，复用上述服务，不建立第二套执行规则 |

### 3.1 平台工具作为内部主入口

当前 V2 已经与平台身份、执行权、确认、effect 记录和事务关联，继续使用直接平台工具可以减少不必要的部署与协议层。权威规范可以通过工具返回结构化属性、说明和示例，不要求所有内容压缩成简短描述符。

### 3.2 RAG 作为参考与发现层

业务资料、长篇教程、案例可用检索帮助定位。若检索命中某个组件案例，员工在生成前仍需读取当前版本的精确合同。检索没有结果不能被解释为组件不存在；检索到了旧案例也不能放宽当前校验。

产品合同本身允许建立搜索索引辅助发现，但明确组件 ID 和版本后的精确获取不能依赖向量相似度。规范读取在 Embedding、向量索引或知识解析不可用时仍应工作。

### 3.3 Skill 提供开发方法

员工的低代码开发 Skill 描述需求澄清、工具调用顺序、错误处理、交付要求。Skill 不硬编码全部产品属性，不保存客户凭据，不替代服务端授权，也不通过脚本直接写数据库实现业务变更。

### 3.4 MCP 保留适配位置

外部 Agent 有接入需求时，Resources 可暴露版本化规范，Tools 可暴露查询、校验和受控操作。外部用户身份必须映射为平台用户及授权上下文；不能默认使用无限权限服务账户。

MCP 接入不改变写入确认、幂等、版本检查或业务事务规则。本批不要求新增 MCP Server，不为内部读取规范强制增加服务部署。

## 4. 目标能力分级与边界

| 层级 | 能力 | 完成判据 |
| --- | --- | --- |
| L1 | 创建基础业务表单 | 必填、选项、布局和页面属性合法，设计器与运行时可用 |
| L2 | 创建关联业务模型 | 多表、关联、子表及平台实际支持的高级组件正确配合 |
| L3 | 创建集成自动化 | 触发器、条件、映射、动作及错误路径符合产品合同 |
| L4 | 修改现有复杂应用 | 先读现状、分析影响、保留数据与无关配置，确认后增量修改 |

各级单独验收，不以 L1 通过宣称 L2/L3/L4 完成。员工能力目录描述允许使用的明确操作，用户 RBAC 决定实际资源与动作范围，不再给员工分配具体应用 ID。

审批工作流、集成自动化和工作流表单设计分别建能力矩阵，不混用名称。定义页、HTML/TSX、自定义脚本、逻辑明细表的开发不随本方案自动开放；当前 T31 的排除范围继续有效，若需支持必须单独补合同和验收。

不承诺创建平台本身没有实现的组件、节点或连接器。遇到不支持的需求，明确给出替代方案或产品缺口，不生成看似合法但运行时无效的字段和节点。

## 5. 空应用从零开发合同

### 5.1 不依赖已有示例

读取应用后，空表单列表是正常状态。员工随后读取平台合同，使用正式默认值和合法示例生成设计，不要求用户先手工创建一个模板。连应用也不存在时，需要用户明确创建意图及相应权限，并经过应用创建确认。

### 5.2 需求信息分为三类

- 用户明确要求：直接进入设计约束。
- 可撤销的展示选择：可以提出合理默认值，例如页面布局与字段展示顺序，并在预览中说明。
- 影响业务语义的未知项：审批人、金额阈值、唯一性、删除规则、外部接口与凭据等，需要确认，不能用行业惯例冒充客户规则。

不要求一次询问所有细节；先澄清阻塞当前设计的关键问题，给出已有明确部分的计划。业务规则未确认时可以给出建议，但不得将建议作为真实规则发布或启用。

### 5.3 从需求到资源的顺序

以“供应商、采购单、采购明细，超过指定金额走后续流程”为例：

1. 明确实体关系、金额口径、审批/自动化类型和测试边界。
2. 读取当前应用及可用组件、节点能力，核实平台是否支持所需行为。
3. 规划资源依赖：基础表单 → 主表/子表或明细结构 → 关联引用 → 自动化。
4. 按正式创建结果获取资源 ID；不编造 appId、formUuid、fieldId 或自动化 ID。
5. 每份设计校验通过后生成具体预览，用户确认后保存。
6. 读取保存结果验证版本和结构，最后汇总已完成、未完成、需配置及未实测项目。

没有知识库时执行同样步骤；只跳过资料检索，不跳过产品合同与校验。

## 6. 权威产品合同服务

### 6.1 单一来源与交付

先盘点设计器默认值、属性编辑器、运行时注册及后端保存规则的差异，再建立统一合同来源。优先采用平台仓库内的版本化结构化定义，供前端生成类型/默认值及后端生成校验资源；不能直接假设现有 TypeScript 类型可以无损生成完整合同。

Rust API 使用随构建交付的合同，不在生产运行时解析前端源码，不依赖运营中心在线服务。初期允许显式维护合同，但必须标记覆盖范围，并以一致性检查防止与产品实现漂移；目标是减少重复手写规则。

每个合同包含：稳定 ID、合同版本、平台发布标识、内容 hash、支持状态、必要的历史兼容说明。已有任务记录用到的合同引用，不把整套规范和密钥存入模型快照。

恢复时当前部署不支持冻结合同，应拒绝直接写入并提示重新读取/设计；不能用旧合同绕过新版本校验。客户端展示名称可以变化，稳定 ID 不随文案修改。

### 6.2 组件合同内容

| 分类 | 必须提供的信息 |
| --- | --- |
| 身份 | componentId、名称、适用 formType、支持状态 |
| 字段结构 | 顶层属性、必填项、ID 规则、父容器与布局约束 |
| props | 类型、默认值、枚举、范围、是否可省略、互斥与依赖关系 |
| 值合同 | 记录值类型、空值语义、默认值格式、读写转换 |
| 交互 | 产品实际支持的禁用、只读、隐藏、校验及联动能力 |
| 关联资源 | 引用目标、目标字段要求、可跨应用与否、资源解析方式 |
| 数据影响 | 唯一约束、持久存储、类型变更及删除影响 |
| 示例 | 最小合法示例、典型配置、非法示例和对应错误 |

高级组件至少逐项核对：子表的父子结构、关联字段的目标与映射、级联选项的数据结构、流水号配置及约束、成员/部门值格式、附件/图片值格式、日期范围和数值精度。这里只列核对对象，不提前承诺产品支持每种高级行为。

前端仅用于渲染的内部状态不得变成 Agent 必填项；持久 Schema 必需字段也不得因 UI 隐藏而从合同遗漏。

### 6.3 Schema 总体合同

完整定义根结构、版本与身份、布局坐标、容器规则、字段唯一性、资源引用、页面属性、formType 限制和规范化行为。合法性判断必须与真实保存后的结构一致。

当前 `platform_get_form_schema_contract` 保持兼容，可先返回目录和能力版本，再按需读取详细组件合同。旧调用方使用的字段不得无版本地改变含义。

### 6.4 自动化节点合同

每个已支持节点提供：nodeType、配置 Schema、默认值、输入输出类型、变量引用语法、可用上游范围、条件操作符、执行副作用、超时/重试、失败路径，以及合法图示例。

区分“创建定义”“保存草稿”“启用/发布”“测试执行”。工具必须返回真实业务状态，不能把保存定义描述为已上线。产品若没有草稿或禁用态，需要如实记录并为创建安全制定对应方案，不能虚构草稿流程。

HTTP 等连接节点还需明确方法、地址与网络策略、请求映射、认证引用、响应解析及错误行为。凭据通过平台配置的引用使用，合同和模型上下文不返回明文密钥。

## 7. 建议工具调整

以下新增名称为提议；实施时先复用已有合同，避免同义重复工具。

| 工具/方向 | 类型与状态 | 职责 |
| --- | --- | --- |
| `platform_get_form_schema_contract` | 现有，只读扩展 | 返回总体规范、支持边界和详细合同入口 |
| `platform_list_component_contracts` | 建议新增，只读 | 按用途/类型查目录，返回 ID、简述和版本 |
| `platform_get_component_contract` | 建议新增，只读 | 精确读取一个或有界多个组件的当前合同 |
| `platform_validate_form_design` | 建议新增，纯校验 | 检查完整设计并返回结构化诊断，不保存 |
| `platform_get_automation_contract` | 建议新增，只读 | 返回节点目录、图规则及变量语法 |
| `platform_get_automation_node_contract` | 建议新增，只读 | 获取节点精确配置与输入输出合同 |
| `platform_validate_automation_design` | 建议新增，纯校验 | 校验图、节点、引用、类型和权限，不执行动作 |
| `platform_update_automation` | 待核对后新增，写入 | 补独立版本化更新预览，确认后调用公共服务 |
| 自动化试运行 | 独立后续能力 | 只对有明确无副作用方案的节点开放，不等同纯校验 |

现有读取 Schema/流程图、创建表单、保存 Schema、T31 补丁、创建自动化和删除等工具继续复用。新旧入口使用同一份公共校验与保存规则。

新增工具按员工明确能力映射，不将“读取表单”扩展为写入，不让通用包装器代表全部操作。既有读取能力需要配套规范读取时，必须显式记录映射的只读语义与版本；新增写动作通过正常运营配置发布，不自动勾选正式员工。

工具描述符保持简洁，详细合同按需加载。先有小目录，再读取本次需要的组件/节点；可以缓存同版本合同，但动态资源和权限必须重新检查。当前 V2 是否支持动态工具发现需要单独核对，首批可以固定少量合同查询工具，不假设已有完整发现机制。

## 8. 校验与错误修正闭环

### 8.1 校验层次

1. 结构：JSON 类型、必填、枚举、范围及未知属性策略。
2. 组件：props 组合、父容器、布局与 formType 限制。
3. 引用：目标应用/表单/字段存在，变量来源与类型一致。
4. 业务：唯一性、聚合或映射规则、自动化可达性及产品特有约束。
5. 权限与影响：用户能否读取设计、写入目标、访问被引用资源，以及删除/变更是否影响已有数据。

纯校验不得创建资源、更新版本、写测试记录、发送通知或请求外部业务接口。若校验需要用户当前无权读取的资源，返回安全的不可验证诊断，不泄露其字段和内容。

### 8.2 结构化诊断

建议统一返回 `code`、`severity`、`path`、`message`、`expected`、`actual`、`relatedResource`、`contractVersion` 和修复提示。其中示例值应脱敏，引用资源只返回用户可见信息。

区分可修复的设计错误、业务信息不足、权限拒绝、资源版本冲突和平台不支持。模型可以按诊断修正后重新校验；不能用删除约束或改成宽松组件的方式悄悄改变用户需求。

模型修正过程中沿用当前执行恢复与无进展处理，不恢复用户已取消的固定运行预算。不新增“运行若干步必须点击继续”的交互。资源冲突须重新读取并生成新预览，不静默覆盖。

### 8.3 校验不授予写权限

校验结果不是保存许可证。预览、批准和实际提交阶段继续重新授权、检查资源版本和冻结参数；完整 Schema/T31 继续要求完整字段可读，部分字段可见时不允许覆盖完整设计。

## 9. 跨资源开发、部分成功与恢复

单个表单保存和单次自动化修改沿用现有事务、effect_key、幂等及 fencing。不能声称多次模型调用和多个资源创建天然构成一个数据库事务。

开发任务需要持久保留资源依赖与实际结果：逻辑名称、真实资源 ID、版本、状态、对应 invocation 和后续依赖。优先复用既有步骤/checkpoint/effect，不预设新建整套项目任务表。

确认按现有工具预览执行，先不新增“批准整个应用即授权所有未来写入”。如未来要做批量确认，必须冻结完整操作集、目标与版本并单独设计，不能把口头同意当作无边界写权限。

示例：供应商表单已创建，但采购单设计失败。任务应报告已创建资源并从失败步骤修正；重启后读取 effect 和已有 ID，不重新创建供应商表单。用户若要撤销，需要查看删除影响并重新确认，不自动删除已创建资源。

测试数据只写明确授权的测试资源；查询验证默认只读。外部通知、HTTP、自动化启用和真实执行按副作用处理。无法安全验证的部分标为未验证，不自动对正式业务试跑。

## 10. 权限、会话与安全边界

- 员工使用权、安装及有效许可证继续保留。
- 模型可用操作来自员工配置能力与平台已实现工具的映射；用户当前 RBAC 与原任务快照决定实际资源访问，管理员规则不突破员工能力上界。
- 不新增员工应用 ID 分配；历史 `applicationIds` 不用于 V2 授权。
- 资源访问按部署、用户、员工、会话隔离；知识检索、工作区与运行恢复不允许跨会话取数据。
- 应用、表单、行、字段、设计查看和编辑权限按操作核对；权限收紧立即生效，运行中新增权限不自动扩充快照。
- 创建、编辑、删除均须用户确认；只读规范查询和无副作用校验无需业务写入确认。
- Skill 环境配置仅注入选中 Skill 的当前调用，不进入合同、模型上下文或公共配置文件。
- 本地脚本不是系统沙箱；不能通过脚本直接访问数据库、内部服务或生成 SQL 来规避业务工具的授权与确认。当前账户执行本身无法提供强制系统级阻断，产品不得宣称已经实现这种隔离。

公共组件规范可不包含客户资源；针对客户资源的可用选项、引用目标和实例示例必须经过授权过滤。合同只说明平台会什么，不能据此泄露客户有什么。

## 11. 员工配置与运营发布调整

运营中心继续负责员工方法、能力选择、Skill 及自带案例，不负责复制每个客户部署版本的完整组件 Schema。规范由客户平台实际版本提供，避免运营包更新与客户端产品版本错配。

建议将员工方法组织为：需求澄清、空应用建模、规范查询、表单设计、自动化设计、校验修正、确认保存、恢复与交付。可以拆成有明确边界的 Skill，不要求为了简单表单读取所有指导。

员工提示词核心要求：

> 先理解需求并读取当前应用。空应用是正常状态，不要求用户提供模板或知识库。使用当前平台合同，不编造组件属性、节点配置、资源 ID 或企业规则。设计先校验，按诊断修正；写入必须通过平台预览、确认和保存工具。业务信息缺失时提出明确问题。最后区分已保存、已启用、已验证和未完成，不用工具成功替代业务完成。

发布步骤：更新能力目录与明确映射 → 编辑员工方法与所需能力 → 保存发布新版本 → 客户平台发现更新 → 正常安装校验 → 新任务获取新能力。活跃任务不自动扩大能力，员工更新不清除会话依赖和已冻结资源版本。

不直接改本地员工包 JSON，不自动全选正式能力，不修改另一个项目中的正式运营商品。本方案若实施，运营中心与客户平台分别提交合同兼容说明。

## 12. 界面与交付表达

沿用 V2 自有组件、HeroUI、MySurface、Gravity 图标，不引入旧 Agent 组件或 CSS Module。先复用已有消息时间线、工具卡和确认卡，不预设新做一个独立 IDE。

工具与消息应关联显示：需求说明 → 规范读取 → 校验诊断 → 修正说明 → 设计预览/确认 → 保存结果。合同查询属于工具活动，不输出私有推理。规范缺失、权限不足、保存冲突等错误应保留可诊断信息。

确认预览突出新增/删除字段、实际 props、关联目标、布局变化、自动化节点/连接变化和已知影响。自动化必须标明保存后是否立即生效；页面不能只展示一大段不可读 JSON。

交付摘要包括真实应用/表单/自动化链接、资源版本、用户确认记录对应结果、测试范围、待配置凭据和未实测行为。不得把仅生成于工作区的 JSON 称为已部署应用。

## 13. 分批实施计划

本计划不抢占已安排的其他专项；用户决定启动后按批推进，不因撰写文档自动修改执行链路。

| 批次 | 具体工作 | 交付与退出条件 |
| --- | --- | --- |
| E0 盘点 | 核对组件/节点、默认值、后端校验、员工能力及现有工具 | 能力覆盖表；每项标记已支持、部分支持、不支持和证据 |
| E1 产品合同 | 建立版本来源，补组件目录、精确合同与总体 Schema | 空应用可获取完整基础规范；高级组件覆盖逐项登记 |
| E2 表单闭环 | 统一纯校验与保存规则，补结构化诊断及修正指引 | 基础表单和选定高级组件从零创建、设计器与运行时验证 |
| E3 自动化合同 | 节点目录、精确合同、变量/类型/图校验、更新工具 | 选定流程可创建和修改；纯校验无副作用，真实状态明确 |
| E4 安全验证 | 明确支持试运行的节点、外部副作用与失败恢复策略 | 可复现验证流程，不调用未授权正式系统、不重复外部效果 |
| E5 员工发布 | 调整 Skill、能力映射、运营正常发布与客户更新 | 正式配置不被自动改写，新任务生效，旧任务兼容 |
| E6 综合验收 | 空应用、多表关系、已有应用修改及故障恢复 | 按下列矩阵形成证据；未测项保留，不宣称全能开发 |
| E7 可选增强 | 知识案例检索、外部 MCP 接入 | 不作为 E1/E2 的必需依赖，复用同一权威合同和业务服务 |

不提前创建全部空 crate、独立微服务、向量数据库或公共 API。确有 DTO 变化时再同步 OpenAPI、生成 SDK 和 BFF；新增持久字段使用增量迁移，不修改历史迁移。

## 14. 验收矩阵

以下是后续验收要求，本次仅编写文档，没有执行这些场景。遵循用户关于测试的最新安排，不擅自启动广泛回归或浏览器测试。

| 编号 | 场景 | 必须证明 |
| --- | --- | --- |
| LC01 | 空应用、无知识库、无既有表单 | 可读取平台合同并完成基础表单，不要求用户提供模板 |
| LC02 | 需求信息缺失 | 对关键业务规则追问，建议与已确认事实分开 |
| LC03 | 通用组件 | 属性、默认值、布局与真实设计器一致 |
| LC04 | 高级组件 | 子表/关联等按选定组件逐项验证，存储和运行行为正确 |
| LC05 | 结构和属性错误 | 返回准确路径及诊断，修正后通过；不静默丢掉业务配置 |
| LC06 | 关联与类型错误 | 非法引用、变量越界、错误映射拒绝，且不泄露不可见资源 |
| LC07 | 自动化从零创建 | 真实节点合同驱动，状态明确，不能仅证明图 JSON 可保存 |
| LC08 | 自动化修改 | 基于版本预览与确认，保留无关节点，冲突后重新设计 |
| LC09 | 纯校验 | 不创建表/记录，不请求外部业务接口，不产生通知 |
| LC10 | 写入确认 | 拒绝无写入，批准使用冻结参数，重复提交效果至多一次 |
| LC11 | 多资源部分成功 | 保留已成功 ID，恢复不重复创建，不自动补偿删除 |
| LC12 | 权限 | 只读用户、字段隐藏、跨应用、批准后撤权及快照限制生效 |
| LC13 | 版本漂移 | 新旧组件合同/部署不兼容时明确拒绝，不按过期规范覆盖 |
| LC14 | 知识缺失和旧案例 | 仍可开发；旧示例不覆盖现行合同；检索故障不阻断规范读取 |
| LC15 | 外部配置缺失 | 说明缺失凭据/连接器，不能声称真实集成已运行 |
| LC16 | Worker 恢复 | 未完成调用和已有效果正确恢复，旧执行权不能提交 |
| LC17 | 产品一致性 | 设计器打开、运行时渲染、版本历史、导航及数据行为一致 |
| LC18 | 员工更新 | 正常发布/安装，新能力只对新任务生效，不扩展旧任务快照 |

每项区分：合同/单元通过、真实数据库/服务通过、真实模型通过、浏览器手动通过、未验证或环境阻断。确定性供应商不能代替真实模型证据，保存成功不能代替运行时和业务验收。

建议综合案例采用明确命名的独立验收应用：供应商、采购单、采购明细及一种平台实际支持的自动化。审批工作流若尚无完整写链路，作为独立未完成项登记，不为了综合案例隐式扩展范围。

## 15. 发布、兼容与完成标准

合同与平台版本一同发布；API、Worker 及前端合同配套，员工包通过正常市场流程更新。先保留旧规范查询响应的兼容性，必要时发布新合同版本，不改变已冻结调用含义。

回退前停止本批活跃设计任务；保留业务数据、资源 ID、effect、确认及历史版本，不删除用户已创建内容，不恢复旧 DSH。旧 Worker 不得接管无法识别的新工具/合同任务。

本专项完成需同时满足：空应用独立开发不依赖知识库、已承诺组件与节点有完整合同、生成与保存使用同一校验规则、跨资源任务可解释且可恢复、权限与确认不退化、实际案例有证据。

完成时只标记已验收的能力等级与组件/节点集合，不使用“支持所有高级组件”“能开发任意业务应用”等无法验证的表述，也不标记完整 AgentV2 或生产发布验收完成。
